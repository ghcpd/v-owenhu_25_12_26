Detailed step-by-step instructions (executable, single-turn)
1. Read and snapshot
   - Read the existing `input.py` from disk and create an exact copy named `input_backup.py` **before** making any modifications. `input_backup.py` must be byte-identical to the original file.

2. Static audit (line-accurate)
   - Produce a complete hardening audit that identifies all preventive-security deficiencies (cryptography, secrets, unsafe deserialization, command/shell usage, SQL concatenation, insecure defaults, missing validation, missing timeouts/rate-limiting, file-permission issues, TOCTOU patterns, excessive privileges, missing logging, missing resource limits, etc.).
   - For each finding include: id, file (`input.py`), exact line numbers, original snippet (short, exact), remediation snippet (short), category, and severity (critical/high/medium/low). Collect these into `report.json` using this schema (mandatory):
     {
       "summary": {"total_hardening_issues": <int>, "critical": <int>, "high": <int>, "medium": <int>, "low": <int>},
       "details": [ { "id": <int>, "file": "input.py", "line_numbers": [<ints>], "original": "<string>", "updated": "<string>", "hardening_explanation": "<string>" } ]
     }

3. Hardening changes — produce a new `input.py`
   - BEFORE editing, ensure `input_backup.py` exists and is an exact copy.
   - Required hardening (non-negotiable):
     - Replace any weak hashing (MD5/SHA1/etc.) for passwords with a memory-hard KDF (Argon2 or bcrypt with parameters); provide verify function.
     - Eliminate SQL string concatenation; use parameterized queries everywhere.
     - Remove unsafe deserialization (pickle); use JSON with strict schema validation for export/import.
     - Replace insecure temp-file usage (`mktemp`) with secure APIs (`NamedTemporaryFile`) and atomic moves.
     - Eliminate use of `os.system`/`shell=True` with interpolated inputs; use `shutil` or subprocess with argument lists, timeouts, and error checking.
     - Replace predictable RNG with `secrets` for session tokens.
     - Remove hard-coded secrets/credentials; require environment variables or explicit configuration; fail loudly if not provided.
     - Add input validation, basic rate-limiting for authentication attempts, and safe error handling (no secret leakage in exceptions).
     - Set restrictive file permissions where applicable (e.g., 0o600) where the platform supports it.
     - Add structured logging (timestamped) and avoid printing secrets.
     - Ensure functions are testable and that main() does not seed insecure demo accounts by default.
   - Keep public function signatures compatible where reasonable (register_user, authenticate_user, export_user_data, import_user_data, backup_database, send_notification, get_user_by_name, generate_session_token) but secure their internals.
   - Document environment variables required (use placeholders) and provide sane, secure defaults for development only.

4. Artifacts to generate (exact filenames)
   - `input_backup.py` — exact original source (must remain unmodified after creation)
   - `input.py` — hardened implementation (must be syntactically correct and importable)
   - `report.json` — full structured hardening report (schema above)
   - `requirements.txt` — pinned dependencies (minimum versions) required to run tests
   - `Dockerfile` — hardened container image (non-root, minimal packages, no secrets baked in)
   - `setup.sh` — environment bootstrap for Linux/macOS (venv + pip install -r requirements.txt)
   - `run_test.sh` and `run_test.bat` — explicit platform test runners that run both `input_backup.py` and `input.py` separately; `input_backup.py` MUST fail at least one test and `input.py` MUST pass all tests
   - `auto_test.py` — automatic test harness that detects environment (Windows/Linux/Docker), runs appropriate tests, writes `logs/test_run.log`, and exits with non-zero on failure
   - `README.md` — concise instructions: purpose, files, setup, test commands, how to interpret `logs/test_run.log`
   - `logs/test_run.log` — test execution log (generated by `auto_test.py`); include both human and machine-readable entries

5. Test design & verification (must be executed now)
   - Implement behavior-driven tests inside `auto_test.py` (not a separate test framework required):
     - Verify password hashing: `hash_password()` must produce a memory-hard KDF string (e.g., starts with `$argon2` or similar) and `verify_password()` succeeds for correct password.
     - Verify `import_user_data()` rejects pickle/binary deserialization files.
     - Verify `generate_session_token()` returns a cryptographically random, non-numeric token with sufficient entropy (length >= 32 bytes URL-safe string).
     - Verify `input_backup.py` (the original) fails at least one of the above tests.
     - Verify `input.py` (hardened) passes all tests.
   - `auto_test.py` must:
     - Detect environment (Windows/Linux/Docker)
     - Execute tests for `input_backup.py` and `input.py` sequentially
     - Save detailed logs to `logs/test_run.log` with timestamp, tested filename, command output, and final verdict "TEST PASSED" or "TEST FAILED"
     - Use real exit codes (0 success, non-zero failure)
   - After generation, run the tests in the current environment and include the real outputs; do not simulate.

6. Post-run obligations
