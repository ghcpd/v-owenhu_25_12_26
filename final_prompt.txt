# Security Hardening Engineer Task: Comprehensive Code Audit and Remediation

## Role & Objective

You are a software security hardening engineer. Your task is to review, audit, and harden the provided source file named `input.py` according to preventive security improvements and industry best practices. This is a single-turn, complete execution task that must deliver all artifacts and verification results without requiring follow-up interactions.

## Inputs & Context

- **Target File**: `input.py` (located in current working directory)
- **Input Source**: The file `input.py` contains code requiring security hardening
- **Working Directory**: Current working directory (all generated files will be created here)

## Comprehensive Security Audit Requirements

### 1. Security Issue Identification

Identify ALL security hardening issues in `input.py`, including but not limited to:
- Insecure default configurations
- Missing security controls or defensive mechanisms
- Weak permissions or violations of the principle of least privilege
- Lack of input validation, resource limits, logging, or safe error handling
- Use of unsafe libraries, functions, or insecure coding patterns
- Missing safeguards such as timeouts, rate limiting, or isolation
- Failure to follow secure coding, deployment, or operational best practices

For each identified issue, report:
- File name
- Exact line numbers
- Issue category
- Severity level (critical / high / medium / low)

**Scope Clarification**: Do NOT focus on exploit-driven vulnerabilities or secret exposure unless they are a direct consequence of hardening deficiencies. The primary goal is to detect non-compliance with preventive security improvements and security best practices.

### 2. Backup Creation (MANDATORY)

Create an explicit, full backup of the original `input.py` named `input_backup.py`:
- `input_backup.py` MUST be an exact copy of the original `input.py` before any modifications
- `input_backup.py` MUST be fully generated and included as a standalone file
- Do NOT describe the backup abstractly or implicitly — the complete source code of `input_backup.py` must be present
- This file must exist independently and remain unmodified after creation

### 3. Code Hardening Implementation

Modify and harden the source code to produce a secure, production-ready version of `input.py`:
- `input.py` MUST contain the hardened implementation with all security improvements applied
- `input_backup.py` MUST remain unmodified after creation
- Both files MUST exist independently and simultaneously
- All identified security issues must be remediated in `input.py`

### 4. Detailed Audit Report Generation

Create a structured JSON file named `report.json` containing:

**Required JSON Structure**:
```json
{
  "summary": {
    "total_hardening_issues": <integer>,
    "critical": <integer>,
    "high": <integer>,
    "medium": <integer>,
    "low": <integer>
  },
  "details": [
    {
      "id": <integer>,
      "file": "input.py",
      "line_numbers": [<list of integers>],
      "original": "<original code string>",
      "updated": "<hardened code string>",
      "hardening_explanation": "<detailed explanation string>"
    }
  ]
}
```

For each hardening improvement in the details array, provide:
- **Hardening issue category**: Type of security deficiency
- **Severity or risk level**: critical / high / medium / low
- **Affected line numbers**: Exact line numbers in original file
- **Original code**: The insecure implementation
- **Updated code**: The hardened implementation
- **Hardening explanation**: Why the original implementation is insufficient from a hardening perspective and how the applied change improves preventive security

**B. Dockerfile**:

**D. .env.example** (if needed):

### 6. Test Execution Scripts

Generate cross-platform test scripts that validate the security improvements:

**A. run_test.sh** (Linux/macOS):
- Bash script with proper error handling
- Must execute tests for BOTH `input_backup.py` AND `input.py` explicitly
- Must clearly report which file is being tested
- Include timestamps and detailed output

**B. run_test.bat** (Windows):
- Batch script compatible with Windows Command Prompt
- Must execute tests for BOTH `input_backup.py` AND `input.py` explicitly
- Must clearly report which file is being tested
- Include timestamps and detailed output

**Critical Test Requirements**:
- The test scripts MUST explicitly test `input_backup.py` and `input.py` as separate test targets
- Tests must be designed such that `input_backup.py` is EXPECTED TO FAIL due to missing security hardening
- Tests must allow `input.py` to PASS when hardening is correctly applied
- Test validation must reflect real, security-relevant behavioral differences (e.g., checking for presence of security controls like input validation, logging, secure hashing, etc.)
- Do NOT use hard-coded exits or simulated results
- Use static code analysis or feature detection to validate security controls

### 7. Automatic Test Execution Script

Implement `auto_test.py` with the following specifications:

**Requirements**:
- Detect the current runtime environment automatically (Windows / Linux / Docker)
- Run the appropriate test script based on detected environment
- Execute tests for `input_backup.py` and `input.py` sequentially
- Use real exit codes to determine success or failure
- Save all logs to `logs/test_run.log`
- Create the `logs/` directory if it doesn't exist

**Log Format Requirements**:
- Include timestamp for each test execution
- Clearly indicate which file is being tested (input_backup.py or input.py)
- Capture complete command output
- Log final status for each file: `TEST PASSED` or `TEST FAILED`
- **CRITICAL**: The log output MUST explicitly show both filenames:
  - `input_backup.py: FAILED` (expected)
  - `input.py: PASSED` (expected)

**Expected Test Outcomes**:
- `input_backup.py` is EXPECTED TO FAIL (contains vulnerabilities, lacks security controls)
- `input.py` is EXPECTED TO PASS (all hardening applied, security controls present)
